# go-sql-benchmark

Benchmarks 15 Go SQL libraries (database/sql, sqlc, sqlx, gorm, ent, go-jet, beego, bun, pgx, pgx_pool, pop, rel, sqlboiler, gorm/gen, xorm) against one seeded
Postgres 15. Numbers are only comparable on the same machine.

## Commands
- `make arch-check` — fails if Go's GOARCH != host arch (emulated runs invalidate results)
- `make db-up | db-down | db-reset` — Postgres 15 via Docker; `db-down` and `db-reset` discard data
- `make db-seed` — re-run `db/seed.sql` against the running DB (truncates, reseeds)
- `make db-check` — verify Postgres major + row counts (`cmd/dbcheck`)
- `make build | vet | test` — `test` strips `BENCH_DSN`, so DB integration tests skip
- `make test-db` — brings the DB up and runs the `Integration` tests
- `make gen | gen-sqlc | gen-ent | gen-jet | gen-sqlboiler | gen-gormgen` — regenerate committed sqlc/ent/jet/sqlboiler/gorm-gen code with tools pinned in `tools/go.mod` (`go tool -modfile=tools/go.mod`); `gen-jet`, `gen-sqlboiler` and `gen-gormgen` read the live schema so they bring the DB up. `gen-gormgen` runs `internal/adapters/gormgen/generate` (build tag `ignore`, so `make build`/`vet` skip it) and restores the old output if generation fails. `make gen-check` fails if regenerating changes any file.
- `make bench BENCH_ARGS="..."` — arch check, DB up, run the matrix, write `results/run-<UTC>.json` (`go run ./cmd/bench -h` lists flags); reseeds the DB on success
- `make bench-cmp A=results/a.json B=results/b.json` — per-cell p95 deviation plus top-5 library check (membership strict; order must match except for libraries whose scores are within `-score-gap`, default 0.02, in both runs; weights from `report/rubric.json`); exit 1 beyond `BENCH_TOL` (make default 0.20; the binary's own `-tolerance` default is 0.10) for stress, or beyond `BENCH_TOL_LOW` (`-tolerance-low`, default 0.60) for the low profile, whose paced few-ms calls have a noisier p95 or when the top 5 differ
- `make report IN=results/x.json [OUT=README.md [DETAILS=REPORT.md]]` — render one result file plus `report/rubric.json` to a short summary (`OUT`: ranking, how to run, environment, methodology) and a detailed report (`DETAILS`, default `REPORT.md` next to `OUT`: per-case tables, pros and cons, qualitative sections); both go to stdout without `OUT`. The hand-written disclaimer and how-to-run text are `internal/report/disclaimer.md` and `usage.md`, embedded; README and REPORT.md are generated, never edit them by hand; exit 1 if a cell or rubric entry is missing, 2 on usage/load errors. Same input gives byte-identical output.

## Decisions
- Go 1.27.3, native arm64, never under Rosetta. `go.mod` has no `toolchain` line; re-check after every `go get`/`go mod tidy`.
- Postgres 15 on host port 55432 (5432 is a native Postgres on the reference machine); override with `BENCH_PG_PORT`.
- `pgx/stdlib` (driver name `"pgx"`) is the shared driver for every `database/sql`-based library; never `lib/pq`.
- Custom runner, not `testing.B`. sqlx is kept and labelled "no updates since 2024".
- Activity filter for candidate libraries: last commit on the default branch (not `pushed_at`, which counts bot branch churn) plus last release. Dropped for inactivity: reform, go-pg, upper/db, gorm_prep (and dbr, godb, gorp, sq earlier); zorm was dropped after it panicked on every read (see Adapter notes).
- A scenario a library cannot express is "n/a (raw SQL fallback)" and is excluded from rankings.

## Layout
- `db/` — `schema.sql` + `seed.sql`, the single source of truth (sqlc reads it; jet generates from the live DB it seeds). Row counts live in `internal/seedcheck.ExpectedRows`; change both together.
- `internal/` — packages; `cmd/` — binaries.
- `internal/bench` adapter contract + profiles; `internal/runner` matrix, cells, stats, reseed store; `internal/result` JSON schema v1 (the Phase 4 contract); `internal/adapters/<lib>` one package per library (`databasesql`, `sqlx`, `sqlc`, `gorm`, `ent`, `jet`, `beego`, `bun`, `pgx` (pgx + pgx_pool), `pop`, `rel`, `sqlboiler`, `gormgen` (library name `gorm_gen`), `xorm`), registered in `cmd/bench` `registry` and `libraryModules`; generated code lives in `sqlc/db`, `ent/entgen` (from `ent/schema`), `jet/gen`, `internal/adapters/sqlboiler/models` and `internal/adapters/gormgen/{entity,query}`. `internal/adaptertest` is the shared integration contract each adapter test calls; `internal/correctness` is the cross-adapter value check. `internal/report` + `cmd/report` render a result file to Markdown (ranking, tables, reasons); `report/rubric.json` is the hand-written data (weights, methodology, pros/cons, cell notes (`feature: true` also prints a note under the feature matrix), and per library flexibility, ease of use, learning curve and community facts with `community_checked`) and must list every library in `registry`. A library with `honorable_mention` set (reason text; currently `pgx` and `pgx_pool`, PostgreSQL-only) is measured and tabled but ranked outside the pool: it takes no rank from the other libraries, is absent from the Top 5 and `benchcmp`, and gets its own report section. The qualitative sections (`internal/report/flexibility.go`, `qualitative.go`) never reach the score, Top 5 or `benchcmp`; `qualscore.go` turns them into a separate qualitative ranking (weights flexibility 8, ease of use 7, community 5; linear level scales; learning curve is a fifth ease criterion; community = last-commit and last-release recency plus open issues per 1,000 stars, no stars), which the report labels as the author's judgement; `combined.go` then prints a last section adding each pool library's measured rank and qualitative rank (equal weight, lowest sum first; details only, never in the score, Top 5 or `benchcmp`); re-read the community facts with `gh api` and update `community_checked` when refreshing. `tools/` is a separate module holding the codegen tools.

## Runner
- Adapter contract: one method per scenario returning rows affected/scanned (runner checks 1/1/1/1/10/40 and counts a mismatch as an error); reads must scan every selected column; no explicit `Prepare`; return `bench.ErrUnsupported` for a scenario the library cannot express (cell becomes `na`); `Init` must work again after `Close`.
- Per cell: reseed, probe once, reseed, fresh pool of `workers` conns, warm-up, measured window. Library order is shuffled per repeat from the recorded seed; per-cell result is the median of `-repeats` (default 3).
- Metrics: latency = per-call service time of successful ops (exact nearest-rank p50/p95/p99, not coordinated-omission-corrected); throughput = ops / wall clock; B/op, allocs/op, CPU ns/op = window deltas (`MemStats`, `getrusage`) / ops and include harness and GC cost (harness floor about 0 allocs/op).
- Profiles (flags override, effective values stored in the JSON): low = 4 workers, 10 ms pacing, 1 s warm-up, 5 s window; stress = 100 workers, unpaced, 2 s warm-up, 10 s window, 400k pre-inserted DELETE ids (window ends early if exhausted).
- Scoring: per case, each of p95, B/op and CPU ns/op is divided by `database_sql`'s value in the same case; a library's score is the weighted geometric mean of those ratios over its ranked cases among insert, update, delete, select and join under both profiles (1.00 = baseline, lower is better). Union is measured, reported in its own ranking and in a feature matrix, and left out of every score, Top 5 and `benchcmp` top-5 check (`scoredScenarios()` in `internal/report/rank.go`). A score never depends on the other libraries, and a case with no ranked baseline or a non-positive metric is not ranked. User-facing text calls a (scenario, profile) pair a "case"; Go code still says cell.
- Value-level correctness: adapters also implement `bench.Verifier` (`ReadModel`, `ReadJoin`, `ReadUnion` return values through the same library query as the benchmarked method; an unsupported scenario returns `ErrUnsupported` on both). `internal/correctness.Check` compares them with the `database_sql` reference (itself checked against golden values from the seed) and replays INSERT/UPDATE/DELETE with a distinctive model (`Right` false). It runs as a pre-flight in `cmd/bench` before every matrix and aborts on any mismatch. Adapter queries have no `ORDER BY`; the check sorts.
- Write semantics every adapter must keep: UPDATE or DELETE of a missing id affects 0 rows (gorm `Save` and ent `UpdateOneID` would not), SELECT of a missing id errors, UPDATE writes every column including zero values.

## Adapter notes (carry into the Phase 4 report)
- Native rule: a scenario is supported if the library's own query API (or, for SQL-first sqlc/sqlx/pgx, its SQL) expresses it; needing the raw-SQL escape hatch means `na`. Current `na`: UNION for gorm, ent, beego, pop, rel, sqlboiler and gorm_gen. Union is unscored, so these n/a cells change no score. Every other cell is measured.
- Insert/Delete counts the library does not report: `bench.DeleteCountUnreported` (pop's Delete returns 1 for any error-free call; `adaptertest` and `correctness` skip the missing-id delete checks and `adaptertest` checks the row is gone instead). beego, pop, rel, sqlboiler and gorm_gen Insert also return 1 without a reported count; `correctness.Check` verifies the stored row.
- Driver exceptions: `pgx`/`pgx_pool` use their own `pgxpool`, `pop` opens its own pool (same pgx stdlib driver); everything else takes the shared `*sql.DB`. zorm was dropped (reads `database/sql`'s private `lastcols`, which pgx stdlib's `RowsColumnScanner` leaves empty). `go.mod` pins `gorm.io/plugin/dbresolver` v1.6.2 because gorm.io/gen v0.3.29 requires v1.5.3, which does not compile against gorm v1.31.2.
- **ent JOIN is edge eager-loading** (`WithCustomer()`): two queries (orders, then their customers), not one SQL JOIN. The report must say so next to ent's JOIN numbers.
- gorm uses `SkipDefaultTransaction` (otherwise every write is wrapped in a transaction), `Joins("Customer")` for JOIN, `Updates` with an explicit column list.
- Reads use each library's idiomatic result handling (sqlx/sqlc/gorm/ent/jet materialise rows; the reference scans into locals), so allocs/op differences include that.
- JOIN filter column: database_sql, sqlx, sqlc, jet, pgx, pgx_pool, pop and rel filter `customers.id`; gorm, gorm_gen, ent, bun, beego, xorm and sqlboiler filter `orders.customer_id` because their query APIs express it that way. `EXPLAIN` gives the same plan for both (the join equality puts them in one equivalence class), so this is left as is.
- Calling `Init` again without `Close` closes the previous pool first (database_sql, pgx, pgx_pool). beego registers its models and one alias once per process; the alias only has to exist for Beego's bootstrap, each `Init` builds its Ormer from its own `*sql.DB`. pgxpool differs from database/sql only by a background health check and 30 min idle / 1 h age limits, none of which reach a measured window; both ping a connection idle for over a second.
- `lib/pq` is linked into the binary (go-jet array literals; ent's generated `migrate` package via atlas) but registers an unused "postgres" driver only; no adapter uses it. All adapters open `sql.Open("pgx", dsn)`.

## Knowledge graph (graphify)
- `graphify-out/` (git-ignored, local only) holds the graph of the code and Markdown docs (`GRAPH_REPORT.md`, `graph.html`, `graph.json`). For architecture or "how does X relate to Y" questions, check `GRAPH_REPORT.md` or run `graphify query "<question>"`, `graphify path "A" "B"`, `graphify explain "X"` before grepping.
- A git post-commit hook (`graphify hook install`; check with `graphify hook status`) rebuilds the code part of the graph after each commit. Doc changes are ignored by it: run `/graphify . --update` (LLM) for those. Manual code refresh: `graphify update .`. Skip the hook once with `GRAPHIFY_SKIP_HOOK=1`.
- The graph is a snapshot: rebuild it after each phase lands, and trust the code over a stale graph.
